## Findings and resolution

### PR #165: retain the date hardening; CSV claim not substantiated

The date field lacks a field-level ceiling, but the claim of unbounded request
processing is overstated: `Server.Handler` installs `limitBody` ahead of CSRF
form parsing; normal requests are capped at 1 MiB, and the mutation requires an
authenticated non-viewer with CSRF protection. This is low-severity defense in
depth, not a demonstrated unauthenticated denial of service.

Implemented one raw `next_run` check using the existing 100-code-point ceiling,
before trimming and before database access. The same check now protects editing
a recurrence. Existing valid dates and creation's empty/invalid-date default are
preserved; rejected requests do not create or change a rule.

The PR does not give a reproducible spreadsheet/version example establishing
`%` or `|` as standalone formula introducers.
[OWASP's CSV guidance](https://owasp.org/www-community/attacks/CSV_Injection)
and [Microsoft's formula operator documentation](https://support.microsoft.com/en-us/excel/calculation-operators-and-precedence-in-excel)
do not substantiate that specific expansion. Left CSV behavior unchanged rather
than altering legitimate text based on an unsupported claim. This is not a
blanket certification of spreadsheet import/export safety: OWASP separately
warns about locale-specific full-width characters and save/reopen behavior.

### PRs #168, #169 and #170: consolidate duplicates and replace stale mocks

All three proposed mock databases return 21 entry columns. Current `GetEntry`
scans 23, including `person_id` and `linked_entry_id`. Each proposed test was
run against the current store using an ignored Go overlay and no database:
all returned HTTP 404 before date validation.

Repairing only PR #169's column count still fails its success case with HTTP 500:
its broad `FROM entries` match supplies a full row to `CreateRecurring`'s
two-column source-lock query. It also recognizes `recurring_rules`, whereas
the actual insertion uses `ExecContext` against `recurring_entries`; its
unconditional mock write success cannot verify persistence.

The three mock helpers do not close their `sql.DB` instances. Their methods
ignore arguments and do not validate actual insertion or context/error behavior.

PR #169 and PR #170 additionally declare the same mock types, helper, test function and
SQL driver name in different files. A combined overlay reproduces a compilation
failure. PR #168 and PR #169 also independently add the same test-file path.

PR #170 checks the trimmed value, so whitespace-padded oversized raw values bypass
its field ceiling. Consolidated validation checks the raw value instead.

Resolution: do not import these duplicate mock suites. Added a small no-database
test verifying early rejection in both handlers and a tagged real-PostgreSQL
integration test covering valid input, the raw 100-character boundary,
oversized ASCII/Unicode padding, preserved defaults and unchanged stored
schedules after rejection. Existing recurring edit/run-now and helper-selection
integration tests remain in place.
